# Assumptions and design decisions

Where the brief left room for interpretation, these are the choices made and the reasons for them.

## Accounts
1. **IDs are UUIDs (v4)** generated by Postgres (`gen_random_uuid()`). They're unique without coordination, and they can't be guessed or counted the way sequential integers can.
2. **`name`** is trimmed, required, and limited to 1–100 characters. Names don't have to be unique, since two customers can share a name.
3. **The request body is strict.** Sending `balance` returns `400 BALANCE_NOT_ALLOWED` with a clear message instead of being ignored silently. Any other unknown field, including `id` or `created_at`, returns `400 VALIDATION_ERROR`.
4. Accounts can't be deleted. They're referenced by immutable ledger entries (`ON DELETE RESTRICT`).

## Money
5. **There's a single currency, shown as INR (₹) in the UI.** The API is currency-agnostic and deals only in numbers.
6. **Amounts are JSON numbers with at most 2 decimal places.** They're stored as `NUMERIC(15,2)`, so the maximum is 9,999,999,999,999.99. Values like `10.123` are rejected rather than rounded, because silently changing money is worse than refusing it. Numeric strings such as `"10"` are rejected to keep the contract strict.
7. **There are no overdrafts.** A balance can never go below 0. This is enforced both in code and by a `CHECK` constraint. Debiting the exact balance down to 0 is allowed.

## Transactions
8. **`reference_id`** is a required string (1–100 characters, trimmed). It's unique per account, and the same value may be used on different accounts.
9. **A duplicate `reference_id` returns `409 DUPLICATE_TRANSACTION`** and includes the original transaction in `details.existing_transaction`. Nothing changes even if the amount or type in the new request differs, because the reference identifies the operation.
10. **The duplicate check runs before the balance check.** A client retrying a debit that already succeeded therefore gets "duplicate", not a misleading "insufficient balance".
11. **`description`** is optional (up to 255 characters). An empty string is stored as `null`.
12. **Each transaction also stores `balance_after`** (the balance right after it was applied) and, for transfer legs, a `transfer_id`. These are additions to the required fields and make the history auditable.
13. **Timestamps** are generated by the database with `clock_timestamp()` and returned as ISO-8601 UTC.
14. **Immutability.** `PUT`, `PATCH` and `DELETE` on transactions return `405 METHOD_NOT_ALLOWED`. A database trigger also blocks `UPDATE` and `DELETE`. A mistake is corrected by posting an offsetting transaction, which is standard ledger practice.

## History, pagination and sorting
15. **Defaults are `page=1` and `limit=20`, and `limit` can't exceed 100.** Values that aren't positive integers, or a limit over 100, return `400 INVALID_PAGINATION`. The API returns an error instead of quietly adjusting the value, so clients notice the mistake.
16. **Asking for a page past the end returns `200` with an empty `data` array** and correct metadata. This isn't treated as an error.
17. **Sorting is `created_at DESC`**, with an internal insertion sequence (`seq`) as a tie-breaker. Two rows written in the same microsecond (for example, transfer legs) therefore still come back in a stable, deterministic order.
18. An invalid `type` filter (anything other than `credit` or `debit`) returns `400 INVALID_TRANSACTION_TYPE`. Leaving the filter out returns both types.
19. The response includes `page`, `limit`, `total_records`, `total_pages`, `has_next_page` and `has_previous_page`.

## Errors
20. **Status codes:**

    | Status | Meaning |
    |---|---|
    | `400` | Malformed input (validation, bad JSON, bad UUID) |
    | `404` | Resource not found |
    | `405` | Method not allowed (immutability) |
    | `409` | Duplicate reference |
    | `422` | Valid request that a business rule refused (insufficient balance) |
    | `413` | Body too large (over 100 KB) |
    | `500` | Unexpected error (details are logged on the server, not exposed) |

21. **A malformed account id** (not a UUID) returns `400 INVALID_ACCOUNT_ID`. A well-formed id that doesn't exist returns `404 ACCOUNT_NOT_FOUND`.
22. **Every error uses the same envelope**, `{ error: { code, message, details?, request_id } }`. `request_id` is also returned in the `X-Request-Id` header for tracing.

## Transfers (bonus)
23. **A transfer creates one `transfers` row and two ledger entries** (a debit on the source, a credit on the destination) in a single database transaction. Each entry gets the system reference `transfer:<transfer_id>`, so it can never collide with references the client chose.
24. **The transfer's `reference_id` is unique per source account.** Repeating it returns `409 DUPLICATE_TRANSFER`.
25. **Transferring to the same account** returns `400 SAME_ACCOUNT_TRANSFER`.

## Scope
26. **No authentication or authorisation.** The brief doesn't mention it. In production, every endpoint would sit behind auth, and accounts would be scoped to an owner.
27. **No rate limiting.** In production it would be handled at the gateway.
28. **Extra endpoints were added for the web console:** `GET /api/accounts` (list and search), `GET /api/accounts/:id`, `GET /api/transfers`, `GET /api/stats`, and `GET /health`. The last one is also used to detect cold starts.
29. **The web console is an addition beyond the brief,** which only asks for an API. It exists to demonstrate the API, the full-stack work, and graceful cold-start handling.
