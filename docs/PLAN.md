# Plan: Transaction Ledger API

This document records how the assignment was broken down and planned before implementation, and how the plan was carried out.

## 1. Understanding the brief

**Goal:** a backend API for a transaction ledger, with accounts, credits and debits, balances, and transaction history. A money transfer between accounts is an optional bonus.

| # | Requirement | Key rules |
|---|---|---|
| 1 | Create account | `name` required. Balance always starts at 0 and the client can't set it. `id` and `created_at` are generated by the system. |
| 2 | Add transaction | `credit` adds and `debit` subtracts. A debit is rejected if the balance is too low. `amount > 0`. `reference_id` is required and unique per account; a repeat returns "already exists" and changes nothing. |
| 3 | Get balance | Returns `account_id` and `balance`. 404 if the account is missing. |
| 4 | Transaction history | Filter by `type`, paginate with `page`/`limit` plus metadata, sorted newest first. |
| 5 | Data integrity | Transactions can't be edited or deleted. The transaction and its balance update happen together or not at all. Balance always equals the sum of valid transactions. |
| 6 | Validation and errors | Correct HTTP status codes and one consistent error format. |
| 7 | **Bonus:** transfer | Debit A and credit B atomically. Both accounts must exist and A needs enough balance. A partial transfer must never happen. |

**Deliverables:** source code, README, API documentation, assumptions.

**What the brief is really testing:** correctness under failure and concurrency (atomicity, idempotency, no overdraft under parallel requests). The CRUD itself is simple. The plan therefore puts most of the effort into the write path and the guarantees around it.

## 2. Technology decisions

| Decision | Choice | Reasoning |
|---|---|---|
| Database | **PostgreSQL** | ACID transactions, row-level locks (`SELECT … FOR UPDATE`), `CHECK`/`UNIQUE`/`FK` constraints, an exact `NUMERIC` type for money, and triggers. The integrity rules can be enforced by the database itself, not only by application code. |
| Runtime | **Node.js + TypeScript** | One language across API and UI. Strict typing for request and response shapes. Well suited to I/O-bound work. |
| Framework | **Express 5** | Minimal and familiar to reviewers. Native async error propagation. |
| Data access | **`pg` + SQL, no ORM** | Transaction boundaries and locks stay explicit and easy to review, which matters most in a ledger. |
| Validation | **Zod** | A single schema gives both runtime validation and static types. |
| Tests | **Vitest + Supertest on real Postgres** | The guarantees live in the database, so mocks would prove nothing. |
| UI (beyond the brief) | **React + Vite + Tailwind + TanStack Query** | Demonstrates the API, covers the full-stack side of the role, and handles cold starts gracefully. |
| Delivery | **Docker Compose**, deployed on **Render** (API), **Vercel** (UI) and **Neon** (Postgres) | Runs locally with one command. Free hosting for a live demo. |

## 3. Data model

```
accounts      id (uuid PK) · name · balance NUMERIC(15,2) CHECK >= 0 · created_at
transactions  id (uuid PK) · seq (identity) · account_id FK · type enum(credit,debit)
              amount NUMERIC(15,2) CHECK > 0 · description · reference_id
              balance_after · transfer_id FK? · created_at
              UNIQUE (account_id, reference_id)
              INDEX (account_id, created_at DESC, seq DESC) [+ type]
              TRIGGER: block UPDATE / DELETE  (immutability)
transfers     id · from_account_id · to_account_id · amount · reference_id · created_at
              CHECK from <> to · UNIQUE (from_account_id, reference_id) · immutable
```

- **Money is never stored as a float.** Balance arithmetic runs in SQL.
- **`balance_after`** on each entry makes the history auditable line by line.
- **`seq`** gives a stable tie-breaker for "latest first" when timestamps are equal.

## 4. Write-path design (the core of the solution)

```
BEGIN
  SELECT … FROM accounts WHERE id = $1 FOR UPDATE    -- serialise writers per account
  duplicate reference_id?   → 409 (checked first, so a retried debit isn't reported as "insufficient")
  debit and balance < amount? → 422
  UPDATE accounts SET balance = balance ± amount
  INSERT INTO transactions (…, balance_after)
COMMIT     -- any error → ROLLBACK, nothing persisted
```

- **Concurrency:** the row lock prevents double-spend and lost updates.
- **Backstops:** the unique constraint covers duplicate requests arriving at the same moment, and `CHECK (balance >= 0)` guarantees no overdraft even if the code had a bug.
- **Transfers:** both rows are locked in ascending id order to avoid deadlocks. The transfer row, the debit leg and the credit leg are written in one transaction.

## 5. API design

- Resource-oriented routes under `/api`, with transactions nested under accounts.
- Success responses look like `{ data }`; lists also carry `pagination` (page, limit, total_records, total_pages, has_next/prev).
- Error responses look like `{ error: { code, message, details, request_id } }`, with stable machine-readable codes.
- Status codes:

  | Status | Used for |
  |---|---|
  | 400 | Validation |
  | 404 | Not found |
  | 405 | Mutating immutable resources |
  | 409 | Duplicate reference |
  | 422 | Business rule (insufficient balance) |

- Documented with OpenAPI 3.1 and served through Swagger UI at `/api/docs`.

## 6. Test plan

| Area | Cases |
|---|---|
| Accounts | Create; zero balance; client-supplied balance or id rejected; name validation; 404 / malformed id |
| Transactions | Credit/debit maths; overdraft rejected with balance unchanged; exact-balance debit; decimal exactness; the spec's consistency example ending at 100 |
| Idempotency | Duplicate returns 409 with balance unchanged; retried debit reports duplicate; same reference allowed on another account |
| Validation | Bad type, amount (≤0, string, >2 decimals, too large), reference, unknown fields, bad JSON |
| History | Newest-first order; type filter; pagination metadata; page past the end; invalid paging parameters |
| Integrity | 405 on PUT/PATCH/DELETE; DB trigger blocks UPDATE/DELETE; DB rejects a negative balance |
| Concurrency | 25 parallel debits leave exactly the right result; 10 simultaneous identical references create exactly 1 row |
| Transfers | Atomic success; insufficient balance; missing account; same account; duplicate; 20 concurrent opposite transfers (no deadlock, total money unchanged) |

## 8. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Race conditions on concurrent writes | Row-level locks, plus constraints as a backstop; covered by concurrency tests |
| Float rounding errors | `NUMERIC(15,2)` and SQL arithmetic; inputs with more than 2 decimals rejected |
| Duplicate submissions or retries | `reference_id` idempotency with a unique constraint |
| Deadlocks in transfers | Deterministic lock ordering |
| Free-tier cold starts (API sleeps when idle) | UI detects slow `/health` and shows a "waking up" state, polling until ready |
| Browser blocking cross-site API calls | Vercel forwards `/api` to the API, so all requests are same-origin |
